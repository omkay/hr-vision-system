# ADR-001: تكامل خدمة الرؤية الحاسوبية employee_activity_tracker_2026 مع نظام Hr_SmartPay

**الحالة:** مقترح (التنقيح الثاني — يحل محل النسختين السابقتين بالكامل)
**التاريخ:** 2026-07-23
**متخذ القرار:** عمر خيرات
**سياق القرار:** موقع واحد (Pilot)، عدد كبير من الكاميرات، زمن استجابة شبه فوري (بالدقائق)، ومناقشة مشروع التخرج بعد نحو شهر واحد

> **ملاحظة على التنقيح:** النسختان السابقتان من هذا المستند كُتبتا اعتمادًا على نسخة قديمة وغير
> ذات صلة من `Hr_SmartPay` (متعددة المستأجرين، تحتوي حافلات/رحلات/رواتب، ولا تحتوي إطلاقًا على
> مفهوم المناطق أو الكاميرات). ذلك الفرع ليس ما يجري تكامله فعليًا. الهدف الحقيقي هو فرع
> `University` — وهو نظام خلفي صغير ومبني خصيصًا لهذا الغرض، يُنمذج بالفعل `Employee`،
> `Zone`، `Camera`، وربط `employee_zone`. هذا التنقيح يتخلّى تمامًا عن إطار "تعدد المستأجرين/النقل"
> ويُصمَّم اعتمادًا على ما هو موجود فعليًا. لا شيء من النسختين السابقتين ينتقل إلى هذه النسخة
> باستثناء واجهة خدمة الرؤية نفسها (لم تتغيّر) وحاويات Docker (تم تحديثها — انظر الانعكاسات).

## السياق (Context)

**`Hr_SmartPay` (فرع `University`)** تطبيق Laravel 12 أحادي المستأجر يضم أربعة نطاقات فقط —
لا يوجد فيه إطلاقًا أي كود لحافلات/نقل/رواتب/تعدد مستأجرين:

| النموذج | الشكل | العلاقات |
|---|---|---|
| `Employee` | الاسم، `job_num` (رقم فريد)، المنصب، وقت البداية/النهاية (الدوام)، `image` | belongsToMany مع `Zone` عبر `employee_zone` |
| `Zone` | مجرد `name` | hasMany مع `Camera`، belongsToMany مع `Employee` |
| `Camera` | الاسم، **ملف فيديو مرفوع**، تنتمي لمنطقة (`Zone`) واحدة | belongsTo مع `Zone` |
| `User` / `Role` | مصادقة مخصّصة بسيطة، الأدوار نصوص مُثبَّتة (HR Manager, CEO, HR Employee) | — |

أهم حقيقة تُوجّه هذا التصميم بأكمله: **`Camera.video` هو ملف فيديو مرفوع** (`POST /camera/add`
يستقبل `multipart/form-data` بامتداد `.mp4`/`.mov`/إلخ، ويُخزَّن على قرص `public`)، وليس بثًا
حيًا عبر RTSP أو تصديرًا من NVR. لا يوجد أي مفهوم لبث مستمر في هذا التطبيق إطلاقًا. هذا يُغيّر
شكل التكامل بالكامل مقارنة بنسختي المستند السابقتين، اللتين افترضتا وجود جهاز GPU يراقب كاميرات
حية ويدفع النتائج للداخل.

**ما هو موجود فعليًا وكانت النسختان السابقتان تفترضان غيابه:**
- المناطق (Zones) موجودة كسجلات مستقلة، ومرتبطة بالفعل بالكاميرات وبالموظفين.
- `Employee.job_num` هو أصلًا المعرّف الفريد والمستقر وذو المعنى البشري — لا حاجة لاختراع عمود
  `vision_key` كما فعلت المسودتان السابقتان.
- `Employee.image` يُجمَع بالفعل عند الإنشاء/التعديل — مصدر جاهز لتسجيل معرض الوجوه، دون الحاجة
  لخط أنابيب صور منفصل.

**ما هو لا يزال ناقصًا:**
- لا يوجد مكان لتخزين نتائج الرؤية — لا يوجد جدول `activity_events`، لا شيء إطلاقًا.
- لا يوجد حقل `type` على `Zone` (`work_area` مقابل `common_area`) — محرك الأحداث الخاص بخدمة
  الرؤية يحتاج هذا لتحديد ما سيُكتشَف (تواجد/عمل/استخدام هاتف مقابل تواجد/تفاعل)؛ اليوم ستفترض كل
  منطقة تلقائيًا وبصمت أنها `work_area` بكامل الإطار إذا مُرِّرت مباشرة إلى `/events/run`.
- لا يوجد مُحفِّز لتشغيل فيديو كاميرا فعليًا عبر خط المعالجة، ولا شيء لاستقبال النتيجة مرة أخرى.
- خدمة الرؤية لا تزال بلا أي مصادقة (دون تغيير عن التنقيحات السابقة — لا يزال يستحق الإصلاح قبل
  تمرير أي لقطات حقيقية عبرها).

**خلل موجود مسبقًا، غير مرتبط بهذا التكامل لكنه يستحق الذكر:**
تستعلم `EmployeeController::showProfile()` (المسار `GET /employee/{token}`) عبر
`Employee::where('qr_token', ...)`، لكن migration جدول `employees` في هذا الفرع لا يحتوي عمود
`qr_token` إطلاقًا. هذا المسار سيُعيد خطأ 500 عند أي استدعاء. هذا المستند لا يتناول هذا الخلل،
لكن من الأفضل عدم التفاجؤ به أثناء أي عرض تجريبي.

## القرار (Decision)

عكس اتجاه تدفّق البيانات مقارنة بالمسودتين السابقتين. لم يعد هناك جهاز GPU منفصل يدفع الأحداث
إلى Hr_SmartPay — **Hr_SmartPay هو من يبادر الآن**. يرفع المسؤول فيديو كاميرا (مبني بالفعل)، ثم
يُشغّل المعالجة؛ يستدعي Hr_SmartPay خدمة الرؤية مباشرة عبر شبكة docker، يستقصي النتيجة، ويخزّنها.
لا حاجة لأي سطح مصادقة وارد (inbound) على Hr_SmartPay لهذا المسار إطلاقًا، مما يُزيل فئة كاملة من
المخاطر التي كان على المسودتين السابقتين التصميم حولها.

```
المسؤول يرفع الفيديو ──► Camera.video (مبني بالفعل)
        │
        ▼
POST /camera/{id}/process  (جديد)
        │
        ▼
Hr_SmartPay ──POST /events/run──► خدمة الرؤية   (نقطة نهاية موجودة، دون تغيير)
        │  تخزين job_id، الحالة=running
        ▼
مهمة في الطابور تستقصي GET /events/{job_id}  (نقطة نهاية موجودة، دون تغيير)
        │  عند الاكتمال:
        ▼
جدول activity_events  (جديد) ── يُربَط عبر employee_id = Employee::where('job_num', key)
```

تسجيل صور الموظفين يتبع نفس النمط أحادي الاتجاه (صادر فقط):

```
إنشاء/تعديل موظف مع `image` ──► POST /enroll على خدمة الرؤية (نقطة نهاية موجودة)
                                  name = (نص) job_num
```

هذا يُبقي خدمة الرؤية كما هي تمامًا اليوم (لا حاجة لنقاط نهاية جديدة هناك) ويحصر كل التعقيد
الجديد داخل Hr_SmartPay، وهو المستودع الذي يجري توسيعه فعليًا.

## نموذج البيانات (Hr_SmartPay — كله جديد وإضافي)

```php
// Migration: إضافة دلالة zone_type التي تفهمها خدمة الرؤية بالفعل.
Schema::table('zones', function (Blueprint $table) {
    $table->string('type')->default('work_area'); // 'work_area' | 'common_area'
});

// Migration: تتبع حالة المعالجة لكل كاميرا.
Schema::table('cameras', function (Blueprint $table) {
    $table->string('vision_job_id')->nullable();
    $table->string('processing_status')->default('idle'); // idle | queued | running | done | error
    $table->timestamp('processed_at')->nullable();
});

// Migration: أين تُحفَظ النتائج.
Schema::create('activity_events', function (Blueprint $table) {
    $table->id();
    $table->foreignId('employee_id')->nullable()->constrained()->nullOnDelete();
    $table->foreignId('camera_id')->constrained()->cascadeOnDelete();
    $table->string('event_type');          // presence | working | phone_use | interaction
    $table->float('start_s');
    $table->float('end_s');
    $table->float('duration_s');
    $table->json('peers')->nullable();     // لأحداث التفاعل
    $table->string('raw_employee_key')->nullable(); // مفتاح job_num كما أُعيد، يُحفظ حتى لو لم يُطابَق
    $table->string('vision_job_id');
    $table->timestamps();
});
```

لا عمود جديد على `employees` — `job_num` (الفريد أصلًا) يخدم كمفتاح هوية الرؤية أيضًا، فقط يُحوَّل
إلى نص عند استدعاء `/enroll` وعند ربط `employee_key` مرة أخرى بـ `Employee`.

## عقد الواجهة البرمجية (API contract)

**صادر فقط (Outbound only)** — Hr_SmartPay يستدعي خدمة الرؤية؛ خدمة الرؤية لا تستدعي مطلقًا للخلف.

```
# عند إنشاء/تعديل موظف، إذا وُجد `image`:
POST {VISION_SERVICE_URL}/enroll
{ "name": "1042", "face_images": ["http://hr-app:8080/storage/employees/xyz.jpg"] }

# جديد: تشغيل معالجة فيديو كاميرا واحدة
POST /camera/{id}/process              (Hr_SmartPay، جديد — محكوم بالأدوار كبقية مسارات الكاميرا)
  → يحوّل camera.video إلى رابط داخلي، وzone.type إلى zone_type
  → يستدعي خدمة الرؤية:
    POST /events/run
    { "video_paths": ["http://hr-app:8080/storage/cameras/abc.mp4"],
      "camera_ids": ["7"],
      "zones": [[{ "label": "desk-area-a", "zone_type": "work_area" }]] }
  → يخزّن { vision_job_id, processing_status: "running" } على سجل الكاميرا
  → يُرسل مهمة طابور تستقصي:
    GET /events/{job_id}   (نقطة نهاية موجودة)
  → عند "done": إدخال دفعي لسجلات activity_events، مع ربط employee_id عبر job_num

GET /camera/{id}/events                (Hr_SmartPay، جديد — نقطة قراءة/تقرير بسيطة)
```

**الفخ الشبكي الوحيد الذي سيضرب بصمت إذا أُهمِل:** رابط `Storage::disk('public')` يُبنى من
`APP_URL` (في `config/filesystems.php`: `rtrim(env('APP_URL', ...), '/').'/storage'`). داخل
Docker، قيمة `APP_URL` هي الرابط الموجَّه للمتصفح `http://localhost:8080` — **غير قابل للوصول من
داخل حاوية `vision-service`**، التي تحل `localhost` إلى نفسها. أي كود يبني رابطًا لتسليمه لخدمة
الرؤية (لفيديو كاميرا، أو صورة موظف) يجب أن يستخدم المضيف الداخلي على شبكة docker
(`http://hr-app:8080`، أُضيف كـ `INTERNAL_APP_URL` في `docker-compose.yml` الخاص بهذا المشروع)،
وليس `asset()`/`Storage::url()` مباشرة. هذا بالضبط نوع الخلل الذي يعمل بشكل جيد على جهاز محمول
ويفشل بصمت (400) داخل حاوية — يستحق تعليقًا في الكود حيث يُستخدَم، لا فقط في هذا المستند.

**المصادقة:** خدمة الرؤية لا تزال بلا أي مصادقة. بما أن Hr_SmartPay أصبح يستدعي للخارج فقط (لا
يستقبل مطلقًا استدعاءات واردة من جهة الرؤية)، فإن الحد الأدنى للإصلاح هو رأس سرّ مشترك (shared
secret) يُرسله Hr_SmartPay وتتحقق منه خدمة الرؤية — إضافة صغيرة إلى
`employee_activity_tracker_2026/service/app.py`، وليس إلى هذا المستودع. إلى أن يتحقق ذلك، أي جهة
تستطيع الوصول إلى المنفذ 8000 يمكنها تسجيل هويات مزيّفة أو قراءة المعرض — لا بأس بذلك على جهاز
محمول، لكن ليس بعد أن يغادر هذا localhost.

## الانعكاسات (Consequences)

- **أبسط بكثير من المسودتين السابقتين:** لا حاجة لعملية منسّق (orchestrator)، ولا سؤال عن نشر
  جهاز GPU، ولا سطح مصادقة وارد على Hr_SmartPay، ولا جدول `employee_checkins` (لا يوجد مفهوم
  كاميرا مدخل في هذا المخطط — كل الكاميرات هي مجرد "لقطات لمنطقة"، لذا فإن تقسيم
  تسجيل الحضور/التحليلات من التنقيح الثاني لا ينطبق هنا وتم إسقاطه).
- **حزم Docker احتاجت إصلاحين حقيقيين**، وليس مجرد تحديث للمخطط:
  1. لم يُشغَّل `php artisan storage:link` إطلاقًا — رفوعات `Storage::disk('public')` (فيديوهات
     الكاميرات، صور الموظفين) ليس لها رابط عام إطلاقًا بدونه، بمعزل عن هذا التكامل. أُضيف إلى
     `entrypoint.sh`.
  2. أُضيف `INTERNAL_APP_URL` إلى `docker-compose.yml` لمعالجة مشكلة الرابط بين الخوادم أعلاه.
     غير مُستخدَم حتى يوجد كود `/camera/{id}/process`، لكنه موثَّق الآن حتى لا يكتشف من سيكتب تلك
     النقطة هذا الخلل بالطريقة الصعبة.
- **لا يزال صعبًا:** لا شيء من `/camera/{id}/process`، أو مهمة الاستقصاء، أو `activity_events`
  موجود بعد. هذا المستند يقترحها؛ لا شيء هنا مُنفَّذ.
- **مكسب مجاني لطيف:** بما أن `employee_zone` موجود بالفعل، فإن أحد التحسينات المستقبلية هو حصر
  مطابقة الهوية على الموظفين المُعيَّنين لمنطقة الكاميرا فقط (مجموعة مرشحين أصغر، أخطاء تعريف أقل)
  — خدمة الرؤية لا تدعم تصفية جزئية للمعرض اليوم، لذا هذا "يستحق معرفة أنه ممكن"، وليس قدرة حالية.

## مخاطر وأسئلة مفتوحة

- خدمة الرؤية بلا مصادقة (انظر أعلاه) — يجب ذكرها كفجوة معروفة، لا كسهو.
- `zones.type` يفترض `work_area` كقيمة افتراضية؛ لم يُقرَّر بعد أي المناطق الموجودة يجب أن تكون
  `common_area` — هذا قرار بيانات لمن يُدخل/يُعدّل المناطق، وليس مشكلة برمجية.
- فيديو واحد مرفوع لكل كاميرا يعني أن "المعالجة" هي بطبيعتها لمرة واحدة، وليست مستمرة. إذا احتاج
  النشر الفعلي إعادة معالجة الكاميرات دوريًا (لقطات جديدة تحل محل القديمة)، فإن `Camera` تحتاج إما
  فيديوهات ذات إصدارات أو تدفّق "استبدال وإعادة معالجة" — لم يُصمَّم هنا، ويُذكَر لأن "شبه الفوري
  (بالدقائق)" كان الهدف المعلَن ونموذج الرفع لمرة واحدة لا يحقق ذلك تلقائيًا دون أن يعيد أحدهم رفع
  اللقطات بانتظام.
- مسار `qr_token` الميت (انظر السياق) سيُربك أي شخص يختبر روابط ملف تعريف الموظف أثناء عرض تجريبي
  — يستحق إصلاحًا من سطر واحد بمعزل عن هذا المستند.

## بنود العمل (Action items)

1. [ ] Migration: `zones.type` (افتراضيًا `work_area`).
2. [ ] Migration: `cameras.vision_job_id`، `cameras.processing_status`، `cameras.processed_at`.
3. [ ] Migration + نموذج: `activity_events`.
4. [ ] ربط `POST /enroll` داخل `EmployeeController::store`/`update` عند وجود `image`، باستخدام `job_num` كـ `name` و`INTERNAL_APP_URL` لرابط الصورة.
5. [ ] `POST /camera/{id}/process` + مهمة استقصاء في الطابور + `GET /camera/{id}/events`.
6. [ ] إضافة تحقق رأس سرّ مشترك إلى خدمة الرؤية (`employee_activity_tracker_2026`، وليس هذا المستودع).
7. [ ] تحديد قصة إعادة المعالجة للكاميرات (رفوعات ذات إصدارات مقابل استبدال وإعادة تشغيل) إذا كان "شبه الفوري" يجب أن يعني أكثر من "عولج مرة واحدة بُعيد الرفع".
8. [ ] (تدبير منزلي، غير مرتبط بهذا المستند لكنه رخيص الإصلاح بالتوازي) إزالة أو إصلاح استعلام `qr_token` الميت في `showProfile()`.
